What is DDD Dropbox?Build plan

Messages can wait. People don’t have to.

A stationary stop
for moving messages.

DDD uses mobile transports—such as a bus driver’s phone—to carry encrypted bundles between disconnected clients and an internet-connected server. A drop box lets the client and the transport visit at different times.

1 / Leave a bundle

A client leaves encrypted bundles at the drop box, then goes. The drop box keeps them ready for a later transport visit.

Illustration of the proposed flow, not live network status. Direct client ↔ transport exchange remains available.

01

One familiar peer for the client.

The client sees another DDD transport. It can leave data at the drop box and still exchange that data with a moving transport later. The drop box can hold many bundles for many clients; it does not need to know which application produced their contents.

02

An explicit relay for the network.

Mobile transports and the server know that this node is stationary. Client routing.metadata records the dropbox relay; the dropbox’s own control bundle records its carrier. A verified binding between the dropbox endpoint and relay identity lets the server join those routes.

A carrier accepting a bundle completes a local handoff. It does not mean the server—or the destination client—has received it yet.

03

The same encrypted bundle, another hop.

Copy relayed user bundles with their original encrypted IDs and bytes. Separately, the dropbox creates and decrypts its own control bundles carrying inventory ADUs and server plans. User encryption endpoints stay unchanged. A new hop still needs integrity checks, trustworthy receipts and regression tests.

Wi-Fi Direct first

Two jobs.
One controlled radio cycle.

The Dropbox alternates on two configurable timers: serve clients, then search for and exchange with transports. Phones keep their existing connection behavior; transports keep hosting.

  1. Host clients
  2. Drain & join
  3. Exchange
  4. Restore hosting

Start each timer when its mode is ready. On expiry, close new admissions and finish active work within a fixed cap before switching. Timer rules & tests · Prototype playground. Group model · Interface concurrency · Asynchronous APIs

Wi-Fi Aware is a later link adapter. Inventory, storage, receipts and routing should remain reusable.

How the dropbox works

The dropbox stores other clients’ encrypted bundles and creates its own control bundles. It reaches the server through passing transports.

  1. Forward queued bundles

    Send all queued upstream bundles like BundleClient, including on the first carrier visit. Inventory reports accompany the flow; sending does not wait for server selection.

  2. Report client acknowledgements

    When a client receives a downstream bundle and acknowledges it, the dropbox persists the acknowledgement and reports it to the server through a control ADU.

  3. Follow server keep/delete instructions

    The server uses upstream receipt and reported client acknowledgements to manage storage. The dropbox retains copies until the server authorizes deletion. KEEP means retain, not stop forwarding.

Periodic switching is the initial radio design. Discovery finds carriers during transport mode; switching early on a discovery event is optional later work. See the timer and role cycle for behavior and tests.

Direction from this brief

Client sees a transport

The client-facing drop box uses the familiar exchange and private lookup. Its identity is classified as a drop box by the server and mobile transports.

Observed mechanism; runtime test required

Unchanged bytes can be copied

The client reuses its latest bundle when no new ADU or ACK requires a new one. Relays forward the original ID and ciphertext. A regression test must prove the full repeated-exchange behavior.

Verified in source

Visits are not fully recorded today

ClientRouting stores counts. Its update is in the received-bundle path after decryption, before the latest-ID check—not a record of every discovery or upload-only visit. Client visit recording adds the missing cases.

Verified in source + planned extension

Reply routing already exists

The server selects all clients mapped to the authenticated transport identity. Reply routing adds the drop-box hop and carrier destination manifests; it does not replace the direct route with GPS routing.

Existing bulk loop; new policy work

Many bundles need explicit queue rules

Current transport inventories can list many files. Bounded subsets, fair priority, durable per-bundle progress and drop-box cleanup are new work in bundle storage and server keep/delete handling/transfer scheduling.

Architectural direction; tests in shared contracts and client visit recording/end-to-end verification

Encryption endpoints stay the same

Reuse client/server encryption and private pickup. The dropbox never receives user-client decryption keys or alters relayed ciphertext. It owns keys only for its own control endpoint. routing.metadata is protected inside endpoint-authored bundles; it is not a mutable relay header.
